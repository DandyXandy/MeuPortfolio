## FASE 7 — Security / Performance ✅

### 1-3. Rate limiting on `/api/request-project` and `/api/continue-project`
- **`src/lib/rate-limit.ts`** (new): in-memory sliding-window limiter, 3 requests per IP per 10 minutes, per route (each endpoint has its own independent bucket). Applied at the very top of both `POST` handlers, before JSON parsing.
- **Why in-memory and not Supabase/Redis**: a Supabase-backed limiter would need a new table (explicitly out of scope — "não alterar Supabase schema" was a hard constraint this phase); Redis/Vercel KV is new infrastructure that isn't justified for this traffic volume. Documented honestly in the module's own comment: this is a **best-effort** defense — the Map lives only while a given Vercel function instance stays warm. It fully covers the actual threat model that matters here (someone spamming the same form repeatedly in one sitting — that traffic lands on the same warm instance), but doesn't guarantee protection against a determined attacker forcing many cold starts on purpose. A cross-instance store (Supabase table or Redis) is the correct upgrade path if this ever becomes a real problem — noted as a pending item, not built now.
- **Verified live** (not just read the code): fired 5 requests from the same simulated IP (`X-Forwarded-For`) at `/api/request-project` — requests 1-3 reached the normal handler logic (returned `500` from the pre-existing "Supabase not configured locally" path, exactly as the project's own README describes — not something I broke), requests 4-5 correctly got `429 {"error":"rate_limited"}`. Confirmed a **different** IP was unaffected (still got the normal `500`, not `429`) and that `/api/continue-project` has its **own independent** bucket (unaffected by `/api/request-project`'s limit for the same IP).
- The client-side wizards needed **zero changes** — both already `throw` on any non-`ok` response and show the existing generic error message ("Não consegui enviar agora... ou me chama no WhatsApp"), which already reads sensibly for a rate-limit case too (the WhatsApp fallback is a real escape hatch). Confirmed by reading `RequestProjectWizard.tsx`'s submit handler.

One pre-existing quirk cleaned up along the way: `Footer.tsx` had **no** `'use client'` directive at all while calling the client-only `useTranslations` hook — it happened to work because it was always transitively inside a client boundary (`SmoothScroll` wraps the whole Home tree) and Turbopack doesn't require every descendant file to redeclare the directive, but it was fragile (it's also rendered directly from server pages like `/planos` and `/projeto/[token]`, where nothing upstream established a client boundary). Mixing verified safe: a Client Component (`SmoothScroll`) receiving Server Components as `children` — composed by `page.tsx` (itself a Server Component) — is the documented, supported Next.js pattern; it's not `SmoothScroll` importing a Server Component itself.

### 5. Framer Motion / AOS / Lenis review
Audited every usage (43 `data-aos` occurrences across 11 files, Framer Motion in 8 files) before touching anything, per the explicit "no refactor grande só por estética" instruction:
- **No real redundancy found** between AOS and Framer Motion — they don't overlap. AOS does exactly one thing (fade-in-on-scroll for static sections: About, Skills, Projects, Plans, Currently, Contact, the case study pages) and does it with zero React state. Framer Motion is used only for things AOS structurally can't do: the Hero's specific staggered entrance + infinite blob loops, the Navbar's mobile menu open/close (`AnimatePresence`, needs exit animations), the two wizards' step-to-step transitions, and `FloatingWhatsApp`'s entrance + glow. **Conclusion: nothing removed** — replacing either would mean rebuilding working, distinct functionality for no real gain, which is exactly the kind of "refactor por estética" the instructions said to avoid.
- **Real gap found and fixed**: `prefers-reduced-motion` was only manually checked in `Hero.tsx` (its 2 infinite blobs + scroll indicator) — `Navbar`'s mobile menu, `FloatingWhatsApp`, and both wizards' step transitions had no reduced-motion handling at all. Instead of patching each file individually (more surface area for mistakes), added a single `<MotionConfig reducedMotion="user">` wrapper in the root `[locale]/layout.tsx` around `{children}` — this is Framer Motion's own global mechanism and now makes **every** `motion.*` animation in the app respect the OS-level `prefers-reduced-motion` automatically, including any added in the future. Hero's manual check was **kept** on top of this specifically for its infinite loops — `MotionConfig`'s reduced-motion mode shortens transition durations, which isn't enough to stop a `repeat: Infinity` animation from still looping (just faster); the manual `animate={reduceMotion ? undefined : {...}}` fully removes the animation, which is the only thing that actually works for an infinite loop.
- **Lenis** (`SmoothScroll`) is still Home-only, same as before — reconfirmed the earlier audit's observation that this makes scroll feel slightly different across the site (Home vs. `/planos`/wizards), but extending it to every page is a visual-consistency call, not a security/performance one, so it's left untouched to respect "não fazer refactor grande" — flagged as a candidate for a later visual-polish pass, not done now.

### Bugs found and fixed by actually running the tools (not just reading code)

- **`STEP_COMPONENTS: Record<WizardStep, React.ComponentType<any>>`** in both wizards (`RequestProjectWizard.tsx`, `ContinueProjectWizard.tsx`) — pre-existing `any`, flagged by lint. My first fix attempt (`React.ComponentType` with no generic) **broke the production build** — `tsc` caught it immediately: `StepSummary` is the one step component that actually takes props (`onEdit`, `isSubmitting`) and is special-cased in the render (`currentStep === 'summary' ? <StepSummary .../> : <StepComponent />`), so the map's value type genuinely wasn't uniform. Real fix: excluded `'summary'` from the `Record`'s key type (`Record<Exclude<WizardStep, 'summary'>, React.ComponentType>`) and moved the lookup so TypeScript narrows `currentStep`/`currentStepId` away from `'summary'` at the point of access (`currentStep === 'summary' ? null : STEP_COMPONENTS[currentStep]`). No more `any`, and it's now actually more correct than before (the old `any` was silently hiding that `'summary'` was never really a valid lookup key). Caught and corrected in the same pass — see the "risks" note below about why this specific fix needed the full loop (lint → typecheck → build) rather than trusting lint alone.
- **`src/lib/pdf/ProjectBriefDocument.tsx`** — unused `Font` import removed; unescaped `"` around "Solicitar Projeto" in the PDF footer text fixed (`&quot;`); and, found while in this file for the lint fix — **the footer referenced a stale, wrong domain** (`dandyabadie.dev`, which isn't a domain this project owns or has ever used) instead of `portfoliodandy.com`. Fixed. This is a real, pre-existing bug — every PDF brief sent to an actual prospective client had the wrong URL in the footer.
